# جولة المنافسة: القلعة تحت الضغط

## مقدمة التحدي

هذه ليست جولة لمن يكتب أطول قائمة من مصطلحات الأمن، ولا لمن يضع «Rate Limit» في عنوان ملف ثم يعلن النصر. المشروع يعمل محلياً أولاً، عربيّاً وعلى الهاتف، وقد اجتاز اختبارات وظيفية كثيرة. الآن جاء الاختبار الذي يفضح العمل الحقيقي: **ماذا يحدث عندما يتوقف الزائر عن التصرف كمستخدم مثالي؟**

إذا كنت ستكرر مشكلة معروفة بلا دليل، أو تبني Demo منفصلاً، أو تغير نصف المشروع لتبدو النتيجة كبيرة، فقد خرجت من المنافسة قبل أن تبدأ. المطلوب كود مقابل كود، ودليل مقابل دليل.

> الفائز ليس من يخيفنا باسم ثغرة، بل من يكتشف نقطة ضعف فعلية بنفسه، يثبتها محلياً، يصلحها بأصغر تغيير صحيح، ثم يحاول كسر إصلاحه ويثبت أن المشروع لم ينكسر.

## الهدف

نفّذ اكتشافاً مستقلاً ثم أصلح **نقطة ضعف واحدة عالية الأثر** مرتبطة بالأمن أو التحمل أو التزامن أو المدخلات أو الاستعادة. لا تفترض أن التقرير المرفق يختار لك المشكلة؛ هو خريطة سياق فقط. لك حرية فحص المشروع كله واتخاذ قرارك، لكنك مسؤول عن البرهان.

الاستخدام الطبيعي المتوقع شخصي وتعليمي، تقريباً 50–300 مستخدم. سيناريو «10,000 عملية متقاربة أو هجومية» هو وسيلة لاكتشاف نقطة الانهيار في بيئة آمنة، **وليس وعداً بأن المشروع يدعم هذا العدد** ولا تصريحاً لمهاجمة أي خدمة عامة.

## الوصول إلى المشروع

اقرأ أولاً [دليل وصول المتنافسين](./AI_CHALLENGE_ACCESS.md). المستودع العام هو مصدر الحقيقة، وفرع `main` هو آخر نسخة. لا تطلب ZIP ولا تبنِ عملك على نسخة قديمة.

| المصدر | الاستخدام |
|---|---|
| `AI_CONTEXT.md` | بنية المشروع والقرارات الثابتة |
| `docs/SECURITY_LOAD_DISCOVERY_REPORT.md` | نتائج اكتشاف سابقة ومخاطر يجب التحقق منها لا تكرارها |
| `package.json` | أوامر الفحص والحزم |
| `drizzle/schema.ts` و`server/` | طبقة البيانات وواجهات التطبيق |
| رابط Render الحي | ملاحظة بصرية فقط، وليس هدفاً للفحص أو الضغط |

قبل أي تغيير سجّل SHA لفرع `main` الذي بدأت منه. استخدم clone نظيفاً وطبّق كل التجارب محلياً أو في بيئة اختبار تملكها أنت.

## المهمة الإلزامية

نفّذ هذا التسلسل، ولا تقف عند الاقتراح:

1. **افحص بحرية.** يمكنك دراسة الواجهة، الخادم، API، الصور، التخزين، الشبكة، قاعدة البيانات، التزامن، البناء، الذاكرة، CPU، وقيود الهاتف.
2. **اختر فرضية واحدة.** صغ نقطة ضعف محددة قابلة للإثبات؛ لا تسرد عشر مشكلات.
3. **أثبتها بأمان.** اكتب اختبار Vitest أو harness محلياً ببيانات تركيبية يثبت السلوك قبل الإصلاح. إن كان القياس ممكناً، اعرض الناتج الفعلي.
4. **أصلحها بأقل تغيير.** لا تعيد كتابة المشروع ولا تستبدل المعمارية بلا ضرورة مثبتة.
5. **هاجم إصلاحك محلياً.** أضف اختباراً عدائياً آمناً يثبت أن الحد أو الحماية يعملان عند تجاوز السيناريو.
6. **شغّل Regression.** نفّذ أوامر الجودة الفعلية المتاحة، ولا تكتب PASS لشيء لم تشغله.

## قواعد غير قابلة للتفاوض

| مسموح | ممنوع |
|---|---|
| فحص محلي/اختباري، بيانات تركيبية، اختبارات وحدات وتكامل قابلة للإعادة | الضغط على Render، GitHub، مزودي AI، قاعدة بيانات حية، أو أي خدمة عامة |
| استخدام الشيفرة الحالية ووثائقها وPatch صغير قابل للتطبيق | استخراج الأسرار أو طلبها أو إضافتها إلى الكود أو التقرير |
| اختبار حدود الصور محلياً بملفات تركيبية | رفع صور مستخدمين أو بيانات حقيقية أو مسح/تعديل بيانات حية |
| إضافة اعتماد واحد فقط إذا برهنت ضرورته وأثرت على الحجم | عشرات الحزم، مشروع Demo منفصل، أو إعادة بناء المشروع |
| تقرير صادق بـ`NOT VERIFIED` عند تعذر بيئتك | اختلاق أرقام RPS أو PASS أو ادعاء «آمن 100%» |

لا تنشئ قاعدة بيانات جديدة، ولا ترحّل قاعدة قائمة، ولا تعدّل إعداد Render، ولا تنفذ اختبار حمل على الإنتاج في هذه الجولة. يمكنك أن تقترح خطة منفصلة إذا ثبت أن الحل يحتاجها، لكن Patch هذه الجولة يظل محلياً ومحدوداً.

## التسليم الإلزامي

سلّم **ZIP صغيراً ونظيفاً** لا يحوي نسخة المشروع الكاملة ولا `node_modules` ولا أسراراً، وبنيته بالضبط:

```text
PATCH.diff
changed-files/
CHALLENGE_REPORT.md
TEST_EVIDENCE.md
SECURITY_SCOPE.md
```

يجوز إضافة `LOAD_SCENARIO.md` فقط إذا نفذت harness محلياً فعلياً. يجب أن يتضمن `PATCH.diff` جميع التغييرات وأن ينجح `git apply --check` على SHA الأساس المعلن.

### محتوى التقرير المطلوب

| القسم | المطلوب بدقة |
|---|---|
| Base | رابط المستودع وSHA الذي بدأت منه |
| Finding | نقطة ضعف واحدة، موقعها، وشروط ظهورها |
| Evidence before | اسم الاختبار/الأمر والناتج الفعلي قبل الإصلاح |
| Minimal fix | الملفات المتغيرة ولماذا هذا أقل تغيير يعالج السبب |
| Adversarial proof | كيف حاولت تجاوز الإصلاح محلياً وماذا حدث |
| Evidence after | أرقام أو نتائج حقيقية عند الإمكان، وإلا سبب عدم القياس |
| Regression | الأوامر التي شغلتها وحالة كل أمر: PASS/FAIL/NOT VERIFIED |
| Impact | أثر التغيير على الهاتف وOffline والحجم والخصوصية والمخطط |
| Verdict | `PASS` أو `PARTIAL` أو `FAIL` مع سبب صريح |

## أوامر القبول

شغّلها فعلياً عندما تسمح بيئتك:

```bash
pnpm test
pnpm check
pnpm build
pnpm perf:check
pnpm mobile:check
```

ولا يعتبر نجاح build بديلاً عن اختبار السلوك. إذا تعذر تثبيت الاعتماديات أو تشغيل أحد الأوامر، اكتب السبب والملاحظة `NOT VERIFIED`، ولا تخترع نتيجة.

## آلية المراجعة والدمج

بعد استلام الحزمة، لا يُدمج شيء تلقائياً. يراجع مدير المشروع بالترتيب: تطبيق Patch على SHA المحدد، مراجعة الأسرار والحجم، إعادة تشغيل الاختبار الجديد، تشغيل Regression المتاح، ثم مقارنة التقرير بالكود الحقيقي. النتيجة تكون: **دمج، طلب إصلاح، أو رفض مبرر**. نسخة المشروع الكاملة لا تعاد إرسالها في كل جولة؛ GitHub هو القناة الدائمة للتقدم.

## السطر الأخير للمتنافس

> أمامك مشروع لم يعد يقبل عبارة «يعمل عندي». ابحث عن نقطة ضعفه الحقيقية، وأثبتها، وأصلحها، وحاول كسر إصلاحك. إن لم تجد شيئاً مثبتاً، قل ذلك بشرف. الكلام الكثير لن ينجو من الـPatch والاختبار.
