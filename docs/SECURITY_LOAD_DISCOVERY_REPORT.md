# تقرير اكتشاف الأمن والتحميل

**الحالة:** قيد الاكتشاف. لا يوصي هذا التقرير بإنشاء قاعدة بيانات أو ترحيلها قبل اكتمال الجرد والاختبارات المقترحة.

## نطاق المراجعة المؤكد

سيُفحص المستودع ضمن هذه المدخلات المستقلة:

1. محرك قاعدة البيانات وإصداره، وDrizzle/driver، والمخطط، والهجرات، والاستعلامات.
2. المصادقة والجلسات ورموز الدخول وصلاحيات المطور.
3. مسارات API والتحقق من المدخلات وحدود الحمولات والتكرار وidempotency.
4. رفع الملفات وتخزينها، ومعالجة الصور، والعمليات الثقيلة والمهلات.
5. التخزين المؤقت وسجل التصميم والطوابير والتوازي.
6. معدل الطلبات والتزامن وpagination وحدود الاستعلامات.
7. متغيرات البيئة والأسرار والنشر على Render ومسار الاستعادة.
8. تغطية الاختبارات الحالية، وفجوات اختبارات الحمل، والمقاييس المطلوبة.
9. مقارنة MySQL على Render وTiDB Cloud وPostgreSQL وفق النتائج، لا وفق تفضيل مسبق.

## شرط القرار

لا يُتخذ قرار قاعدة البيانات أو الترحيل إلا بعد تحديد المحرك الحالي، وحصر الفجوات، وكتابة خطة هجرة وتراجع قابلة للاختبار، وتعريف مؤشرات قبول للتحميل تشمل RPS والتزامن وP95/P99 ونسبة الخطأ واستهلاك CPU/RAM واتصالات قاعدة البيانات.

## 1. جرد قاعدة البيانات والـORM — مكتمل

### المحرك الفعلي

أثبت الاستعلام القرائي المباشر أن قاعدة المشروع الحالية هي **TiDB Serverless 8.5.3** بالإصدار المعلن `8.0.11-TiDB-v8.5.3-serverless`، مع توافق MySQL 8.0. اسم القاعدة هو معرف المشروع، ولا تُعرض أي بيانات اتصال أو أسرار في هذا التقرير.

يؤكد المستودع الاعتماد نفسه: `drizzle-orm` 0.45.2 مع driver `mysql2` 3.15.0، وDrizzle Kit مضبوط صراحة على dialect `mysql`. لذلك فـ **MySQL/TiDB هو المحرك الحالي الحقيقي**، وليس PostgreSQL.

### الجداول والعلاقات

| الجدول | الغرض | الفهارس/العلاقات الملحوظة |
|---|---|---|
| `users` | الحسابات والجلسات والأدوار والإيقاف | مفتاح رئيسي و`openId` فريد |
| `access_codes` | رموز دخول مجزأة غير خامة | `codeHash` و`sessionOpenId` فريدان |
| `developer_providers` | مزودو AI ومفاتيحهم المشفرة | مفتاح `id` فقط |
| `app_announcements` | رسائل المطور العامة | مفتاح `id` فقط |
| `user_messages` | رسائل المستخدمين للمطور | FK على `users.id` وفهرس `userId` |
| `__drizzle_migrations` | سجل تطبيق الهجرات | داخلي لـDrizzle |

### الاستعلامات وأنماط الاعتماد

يغطي التطبيق حالياً upsert للمستخدمين، redeem ذرياً لرموز الدخول، إدارة مزودي AI، الرسائل، الإعلانات، وحالة المستخدم. توجد معاملات صريحة عند إبطال رمز دخول مع تعطيل الحساب المرتبط. توجد عمليات `onDuplicateKeyUpdate` خاصة بـMySQL/TiDB، واستخدام `mysqlTable` و`mysqlEnum` و`onUpdateNow`، لذلك الانتقال إلى PostgreSQL **ليس تبديل سلسلة اتصال فقط**؛ يحتاج تحويل schema وdriver وبعض تعابير الاستعلام واختبارات انحدار.

### فجوة هجرة حرجة

سجل المشروع يحتوي snapshots وjournal لأربع هجرات مسماة، لكن مجلد `drizzle/migrations/` لا يحتوي ملفات SQL الملتزمة، بينما سجل قاعدة البيانات الفعلي يحوي صف هجرة واحداً فقط. المخطط الفعلي موجود ويطابق الجداول الأساسية، لكن لا توجد حالياً سلسلة SQL قابلة لإعادة بناء قاعدة جديدة أو استعادة دقيقة من Git. هذه فجوة **P0**: يمنع اتخاذ قرار ترحيل أو إنشاء قاعدة إنتاج قبل إنشاء مسار schema/migration قابل لإعادة التشغيل واختبار تراجع موثق.

## 2. مسارات المصادقة والملفات والعمليات الثقيلة — مكتمل

### المصادقة والجلسات

يوجد فصل واضح بين ثلاثة مستويات: جلسة مستخدم JWT موقعة بـ`JWT_SECRET`، وجلسة مطور HMAC قصيرة (8 ساعات)، ورمز وصول مخزن كبصمة SHA-256 مع تفعيل ذري للاستخدام. كلمات مرور المطور ومفاتيح مزودي AI تبقى على الخادم، ومفاتيح المزودات تُشفّر بـAES-256-GCM قبل التخزين. كما أن مقارنة كلمة مرور المطور تستخدم مقارنة ثابتة زمنياً عند تساوي الطول.

لكن مسار `developer.login` ومسار `accessCodes.redeem` عامان ولا يملكان rate limit أو قفل محاولة أو مراقبة محاولة فاشلة. كما أن إنشاء سياق tRPC يحاول تحليل جلسة كل طلب قبل معرفة إن كان المسار عاماً. هذا مقبول لحجم شخصي صغير، لكنه لا يمثل حدّاً إنتاجياً عند استقبال زيارات أو محاولات تخمين كثيفة.

### التحقق من الإدخال والحجوم

يوجد Zod على أغلب إجراءات tRPC، مع حدود مفيدة للنصوص والصفحات والألوان والرموز. يحد مسار Try-On قيمة صورة Data URL إلى 12,000,000 محرف، ويحد Perfect Corp الصور إلى أقل من 10MB وPNG/JPEG فقط. مع ذلك، بوابة Express تقبل `json` و`urlencoded` حتى **50MB** عالمياً، قبل تمييز المسار أو المستخدم. هذا أكبر من الحد الفعلي للصور ويتيح حمولة كبيرة لمسارات لا تحتاجها.

### الملفات والتخزين

تخزين النتائج يستخدم Forge/S3 عبر أسرار خادم، ويضيف لاحقة عشوائية إلى المفتاح. هذه الأسرار لا تصل للواجهة. لكن نسخة Render لا تملك تلقائياً أسرار Forge، لذلك لا تعمل وظائف حفظ نتائج Try-On أو proxy التخزين خارج بيئة المشروع من دون بديل تخزين مستقل. كذلك مسار `/manus-storage/*` يعيد توجيه أي مفتاح صالح من دون تحقق مستخدم داخل التطبيق؛ يجب اعتبار مفاتيح الكائنات غير قابلة للتخمين، لا طبقة تفويض كاملة.

### العمليات الثقيلة

تشغيل Try-On وإزالة الخلفية السحابية يحدث **داخل طلب المستخدم نفسه**. يجري التطبيق استدعاء مزود خارجي، ثم استطلاع متكرر حتى 20 مرة كل 3 ثوانٍ لمسار Try-On، أو حتى 30 مرة كل ثانيتين لمسار Perfect Corp، ثم تنزيل نتيجة قد تصل إلى 15MB ورفعها للتخزين. لا توجد queue أو worker أو حد تزامن أو idempotency key أو rate limit حول هذه العمليات.

استدعاء LLM يملك retry بحد أقصى أربع محاولات وbackoff، لكنه لا يضع `AbortController` أو timeout صريحاً على fetch. تحت تعطل مزود خارجي، تبقى المحاولات والانتظار ضمن request حي وقد تضخم زمن الاستجابة واستهلاك العامل. المسار المحلي لإزالة الخلفية في المتصفح لا يحمل هذا العبء على الخادم، وهو المسار الآمن الافتراضي حالياً.

### ملاحظات مرجعية عن Render

تؤكد وثائق Render أن MySQL يمكن تشغيله كخدمة خاصة، لكنه يتطلب قرصاً دائماً عند `/var/lib/mysql` للحفاظ على البيانات، وأن القرص الدائم غير متاح للخدمات المجانية ويمنع النشر بلا انقطاع. وتؤكد الوثائق أيضاً أن Render Postgres خدمة مختلفة تستخدم عناوين PostgreSQL؛ لذلك لا يجوز معاملتها كبديل متوافق مباشرة مع schema/driver MySQL الحالي. ## 3. حدود الطلبات والتزامن والمرونة التشغيلية — مكتمل

| المجال | الوضع المثبت حالياً | الأثر عند حمل أو إساءة استخدام | الأولوية |
|---|---|---|---|
| Edge / CDN | لا توجد طبقة محددة في المستودع | يصل الطلب مباشرة إلى Express | P1 |
| Body size | حد عالمي 50MB لـJSON وurlencoded | حجز ذاكرة غير ضروري لمسارات صغيرة | P0 |
| Rate limit | لا توجد طبقة IP أو session أو user | تخمين رموز/دخول أو تكرار Try-On بلا سقف | P0 |
| Validation | Zod وحدود جيدة لكثير من RPC | لا تغطي حجم الجسم قبل parser ولا معدل الاستدعاء | P1 |
| Duplicate submissions | claim رمز الدخول ذري؛ بقية mutations بلا idempotency | تكرار الرسائل وعمليات AI عند إعادة الإرسال | P1 |
| Heavy work | Polling ومزودات داخل request | استنزاف عمال وارتفاع latency عند بطء المزود | P0 |
| Queue / worker | غير موجودين | لا توجد حدود concurrency أو إعادة تشغيل مهمات آمنة | P0 |
| Cache | cache محلي للمتصفح فقط | لا يوجد cache/response protection على الخادم | P2 |
| Pagination | Heartbeat فقط اختياري؛ قوائم المستخدمين/الرسائل/المزودات غير مقسمة | نمو الجداول يرفع زمن وذاكرة الردود | P1 |
| DB pool | اتصال Drizzle كسلسلة URL من دون إعداد pool ظاهر | حدود الاتصالات والطابور غير معرّفة أو مرصودة | P1 |
| Timeouts / breakers | timeout 8s فقط لاختبار مزود؛ LLM وعمليات الصور لا تملك hard timeout مركزي | طلبات معلقة وإعادة محاولات مضخمة | P0 |
| Observability | لا توجد metrics/health endpoint/trace أو أداة load test مخصصة | لا يمكن إثبات P95/P99 أو CPU/RAM أو اتصالات DB | P0 |
| Backup / restore | لا توجد scripts للنسخ أو اختبار استعادة | لا يوجد دليل استعادة صالح للبيانات | P0 |

### حدود الاستعلامات والتكرار

رمز الدخول يملك claim شرطياً في SQL يمنع تجاوز `maxUses` عند وصول طلبين متسابقين؛ هذه نقطة قوة حقيقية. بالمقابل، رسائل المستخدمين وبدء Try-On وإزالة الخلفية وتوليد النص لا تستخدم مفتاح idempotency. القوائم الإدارية للرسائل والمستخدمين والإعلانات والمزودات ترجع النتائج كاملة بلا cursor أو حد صفحة. يجب إضافة pagination قبل اعتبارها مناسبة لبيانات متنامية.

### قابلية التحمل الحالية

لا توجد أداة اختبار حمل في الحزم أو المستودع، ولا endpoint صحة أو metrics تشغيلية مميزة عن «metrics» التصميم المحلية. لذلك لا يوجد رقم RPS أو عدد مستخدمين متزامنين أو P95/P99 أو نسبة خطأ أو استهلاك CPU/RAM أو اتصالات DB يمكن نسبته للتطبيق حالياً. أي ادعاء سعوي قبل بناء اختبار ومراقبة سيكون غير موثق.

### حدّ الاختبار المقبول مستقبلاً

لن يستخدم التقرير عبارة «يدعم 100 ألف مستخدم». معيار القبول المقترح قبل نشر عام هو سيناريوهات موثقة وواقعية: قراءة عامة، redeem رمز، إرسال رسالة، وعمليات ثقيلة مرفوضة أو مؤجلة بعد بلوغ السقف. يُقاس لكل سيناريو RPS، المستخدمون المتزامنون، P50/P95/P99، نسبة الخطأ، CPU/RAM، وعدد اتصالات DB، مع اختبار مهاجم واحد يرسل حمولات كبيرة وتكراراً سريعاً. لا تبدأ هذه الاختبارات ضد الرابط العام أو مزودات AI المدفوعة قبل عزل بيئة اختبار وسقف تكلفة وموافقة صريحة.

## 4. مقارنة بدائل قاعدة البيانات — مكتمل

| الخيار | التوافق مع الكود الحالي | التشغيل والاستعادة | قرار الاكتشاف |
|---|---|---|---|
| MySQL 8 كخدمة خاصة في Render | عالٍ؛ يحتفظ بـ`mysql2` وDrizzle MySQL ونمط upsert الحالي | يتطلب خدمة Docker خاصة وقرص `/var/lib/mysql`؛ يلزم backup منطقي بـ`mysqldump` ولا تكفي snapshot القرص للاستعادة | قابل، لكن تكلفة تشغيلية ومخاطر أعلى على مشروع هاتف شخصي |
| TiDB Cloud | عالٍ مبدئياً؛ المحرك الحالي نفسه TiDB/MySQL 8 compatible | مستقل عن Render، ما يحسن فصل فشل الاستضافة عن البيانات؛ يجب فحص TLS/اتصال `mysql2` وخطة backup مع المزود | المرشح التقني الأول **بعد** إصلاح الهجرات واختبار اتصال منعزل |
| Render Postgres | منخفض من دون ترحيل | قاعدة مدارة جيدة، لكن تستخدم URL/driver/schema PostgreSQL مختلفاً | مرفوض في المرحلة الحالية؛ يدرس فقط كمشروع ترحيل مستقل |

### سبب عدم اختيار مسبق

النمط الحالي لا يستخدم stored procedures أو triggers أو FULLTEXT أو خصائص TiDB غير المدعومة التي تحذر منها وثائق TiDB، ولذلك لا توجد مخالفة ظاهرة تمنع الانتقال بين MySQL 8 وTiDB على مستوى الاستعلامات الحالية. لكن هذا ليس برهان توافق إنتاجي؛ يلزم اختبار migration وqueries الفعلية قبل القرار. [4]

يتطلب خيار Render MySQL تشغيل خدمة MySQL خاصة مع Docker وقرص persistent في المسار المحدد، وتوصي وثائقه بالنسخ المنطقي عبر `mysqldump` بدل الاعتماد على استعادة snapshot قرص لقاعدة بيانات مخصصة. [1] [2] وهذا يبقي مسؤوليات database operations (backup، restore، update، monitoring) على المشروع.

أما PostgreSQL فيحتاج driver `pg`، واستبدال `mysql-core` بـ`pg-core`، وتحويل `mysqlTable` و`mysqlEnum` و`onDuplicateKeyUpdate` ونتائج `insertId` وإعادة إنشاء كل الهجرات. توثق Drizzle أن PostgreSQL يستخدم dialect وdriver وإعداد اتصال مختلفين. [6] لا يوجد في نتائج المستودع سبب معماري يبرر هذا التحويل الآن.

## 5. خطة حماية الإنتاج والهجرة والتراجع — مقترحة، غير منفذة

### البنية المستهدفة

> **CDN/Edge → Rate Limit → Request Validation → API → Queue/Worker للعمليات الثقيلة → Cache → Database**

هذه طبقات مستقلة؛ زيادة سعة قاعدة البيانات لا تعالج إساءة استخدام الحافة أو تكرار طلبات الصور أو بطء مزود AI.

| الطبقة | التنفيذ المقترح | شرط البدء |
|---|---|---|
| CDN/Edge | تفعيل حماية DDoS/WAF ومحددات حجم قبل Express في مزود الاستضافة/الـEdge | تحديد نطاق الإنتاج النهائي |
| Rate limit | مخزن موزع مشترك، لا memory محلي؛ مفاتيح IP + session + user بحسب المسار | اختيار cache/KV خارجي |
| Validation | تقليل body العام وإضافة limit خاص لمسار الصورة؛ تدقيق MIME وأبعاد/بايتات الصورة | بعد تصميم مسار upload منفصل |
| API | Zod موجود ويستمر؛ إضافة idempotency للرسائل وبدء مهام AI | إضافة جدول مفاتيح أو قيود فريدة |
| Queue/Worker | تحويل Try-On والإزالة السحابية إلى job محمي بحالة واستعلام حالة؛ concurrency يبدأ بـ1 | إعداد worker وتخزين للمهام |
| Cache | CDN للملفات العامة فقط، وcache قصير للقوائم العامة الآمنة؛ لا cache لجلسات أو رموز | تعريف صلاحية كل مورد |
| Database | pool صريح محدود ومراقب، فهارس pagination، اتصال داخلي TLS عند الحاجة | اختيار محرك قاعدة البيانات |
| Observability | صحة الخدمة، structured logs، metrics للـlatency/error/CPU/RAM/DB connections/queue | قبل اختبار حمل جاد |

### حدود أولية لا تُعد وعود سعة

القيم التالية نقاط بداية للاختبار وليست اتفاقاً على قدرة إنتاجية: تخفيض JSON العام إلى 256KB، وضع صورة كبيرة في endpoint منفصل مقيّد بالبايتات والأبعاد، حد محاولات دخول/رمز لكل IP وsession، وحد أقسى متحفظ لمهام AI لكل مستخدم. تُضبط الأرقام النهائية فقط بعد نتائج load test وخصائص مزودات AI وكلفة التشغيل. المسار المحلي لإزالة الخلفية لا يدخل طابوراً ولا يحتاج خدمة خارجية.

### خطة الهجرة والاستعادة الإلزامية

1. **إصلاح المصدر أولاً:** إنشاء baseline SQL قابل للإعادة من المخطط الفعلي، ثم إدخال كل SQL migration لاحق في Git مع checksum.
2. **بيئة اختبار معزولة:** إنشاء قاعدة جديدة بلا بيانات إنتاج، تطبيق baseline، ثم تشغيل اختبارات schema وrouter وaccess-code عليها.
3. **نسخ منطقي قابل للقراءة:** أخذ export منطقي ومشفّر، والتحقق من عدد الصفوف وبصمات الجداول، ثم تنفيذ restore تجريبي إلى قاعدة معزولة.
4. **ترحيل توسعي فقط:** إضافة جداول/فهرس/أعمدة اختيارية أولاً؛ لا حذف أو إعادة تسمية أو تغيير نوع في نفس إصدار التطبيق.
5. **نشر متوافق:** نشر التطبيق الذي يفهم المخطط القديم والجديد، تطبيق migration واحد، قياس الصحة، ثم إزالة القديم في إصدار لاحق بعد فترة مراقبة.
6. **تراجع:** يعاد التطبيق إلى commit سابق فقط إن كان المخطط متوافقاً. لا rollback DDL أعمى؛ تستخدم migration تصحيحية forward-only أو restore مجرّب عند فشل البيانات.

### خطة اختبار الحمل قبل اعتماد الإنتاج

ينشأ ملف اختبار منفصل على بيئة staging ويقيس سيناريوهات read، redeem رمز، رسالة، وبدء مهمة ثقيلة. يمنع تشغيلها على الإنتاج أو مزود مدفوع من دون سقف كلفة وموافقة.

| القياس | ما يوثق | شرط النجاح |
|---|---|---|
| RPS والتزامن | مستوى ثابت ثم زيادة تدريجية لكل سيناريو | لا انهيار أو نمو غير محدود في الطابور/الاتصالات |
| P50/P95/P99 | latency لكل endpoint | هدف موقّع بعد خط أساس، لا رقم مختلق مسبقاً |
| نسبة الأخطاء | 4xx و5xx والمهلات | الحماية ترفض الزائد بوضوح بدلاً من تعطيل الخدمة |
| موارد الخدمة | CPU وRAM واتصالات DB والـevent loop | تبقى ضمن الحدود ويظهر alert قبل التشبع |
| سلوك الإساءة | IP واحد وحساب واحد يرسلان payloads وتكراراً سريعاً | يوقفان عند edge/rate limit ولا يمنعان المستخدمين الطبيعيين |
| الاستعادة | restore لعينة قاعدة وreplay للهجرات | تطابق مخطط وcounts وتعمل مسارات الدخول |

### قرار ما قبل التنفيذ

لا تنشأ قاعدة جديدة الآن. الأولوية هي: **P0-1** baseline migrations واختبار restore، **P0-2** rate limit/body limits/idempotency، **P0-3** queue للعمليات الثقيلة وmetrics، ثم اختبار staging. بعدها يعاد تقييم MySQL على Render مقابل TiDB Cloud بنتائج اتصال وحمل حقيقية. PostgreSQL يبقى خياراً مؤجلاً لمشروع ترحيل مستقل.
