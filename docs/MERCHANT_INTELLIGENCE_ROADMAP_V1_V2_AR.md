# خارطة Merchant Intelligence — مرحلتان للتاجر

## القرار

الفكرة ليست مجرد شريط أوامر. المنتج المقصود هو **مساحة رابعة مستقلة باسم «المساعد»** في التنقل السفلي، إلى جانب **إنشاء** و**دفعات** و**الإعدادات**. هذه المساحة ترافق التاجر عند البداية، تجمع تفضيلات المتجر بموافقته، وتقترح تعديلات تصميم منظمة، ثم تساعده أثناء استخدام التطبيق من دون أن تجعل إنشاء الإعلان مرهوناً بالإنترنت أو بنموذج ثقيل.

> «التعلم» في المرحلة الأولى يعني تذكّر تفضيلات صريحة وإشارات استخدام محلية قابلة للمسح، وليس تدريب أوزان نموذج لغة خفية على الهاتف.

## المرحلة الأولى — Merchant Assistant Foundation

### النتيجة التي يراها التاجر

عند فتح صفحة **المساعد** لأول مرة، يمر التاجر في حوار قصير من 4–6 خطوات. يسأل المساعد عن اسم المتجر، المدينة أو الموقع الاختياري، رقم التواصل أو واتساب الاختياري، فئة الملابس، والثيم أو الألوان المفضلة. يستطيع التاجر الإجابة بجملة واحدة أو تخطي أي سؤال. لا تحفظ المعلومة قبل أن يعرض المساعد ملخصاً واضحاً ويطلب التأكيد.

بعد الإعداد يصبح المساعد مساحة عملية، لا محادثة للزينة. يقترح إجراءات مثل «اعتمد النمط الليلي لعرض فاخر» أو «كبّر القطعة قليلاً ضمن المنطقة الآمنة»، ويقبل أوامر عربية واضحة. كل اقتراح يبين **ما الذي سيتغير** ويقدم زري **تطبيق** و**تراجع**. ينتج التطبيق الإعلان عبر المحرك الحالي ثم يعيد تشغيل DesignContract وQuality Gate.

| طبقة المرحلة الأولى | مسؤوليتها | لا يسمح لها به |
|---|---|---|
| واجهة المساعد | حوار الإعداد، عرض الاقتراح، التأكيد والتراجع | تغيير الإعلان صامتاً أو حفظ معلومات من دون تأكيد |
| Merchant Profile المحلي | اسم المتجر، التفضيلات الصريحة وإشارات استخدام قليلة | محادثة كاملة، صور، أسرار، أو ملفات اعتماد |
| Rules-first parser | فهم الأوامر العربية الواضحة وتحويلها إلى typed commands | التخمين في الأوامر الغامضة أو تنفيذ نص حر |
| Command reducer | تطبيق allowlist على إعدادات التصميم الحالية | تعديل Canvas أو React أو DesignContract مباشرة |
| Insight draft | صياغة ملخص تحسين للمطور من إشارات محلية | الإرسال التلقائي أو كشف بيانات التاجر |

### التنقل الرابع

تضاف تبويبة رابعة باسم **«المساعد»** بأيقونة واضحة، من دون كسر ترتيب الإنشاء والدفعات والإعدادات أو زيادة CSS كبير. تبقى الصفحة lazy-loaded ولا تحمّل نموذجاً عند فتح التطبيق أو عند فتح تبويبة المساعد. في وضع اختبار الأصدقاء، تعمل ميزات الإعداد والأوامر المحلية، بينما يبقى أي إرسال إلى المطور مخفياً أو معطلاً لأنه يحتاج موافقة ومسار مصادقة صالحاً.

### ذاكرة وتعلم محليان

يحفظ التطبيق تفضيلات مؤكدة فقط، مثل الثيم المفضل وحجم المنتج المفضل وظهور العنوان والألوان الافتراضية وبيانات المتجر. يمكنه حفظ عدادات مجمعة قليلة مثل «رُفض اقتراح الثيم الليلي 3 مرات» أو «تم اعتماد تكبير القطعة مرتين». لا تحفظ النصوص الكاملة للأوامر بعد تحويلها، ولا تسجل ما يكتبه التاجر في تقرير مخفي.

يحوّل المساعد تلك الإشارات إلى **مسودة ملاحظة للمطور** مفهومة، مثلاً: «يطلب المستخدمون حجماً أكبر للسعر، لكن هذا الإعداد غير مدعوم حالياً». لا تُرسل المسودة تلقائياً. يراجعها التاجر ويحذف أو يوافق على إرسالها عبر قناة رسائل موجودة ومصادق عليها في المستقبل؛ إلى أن تتوافر قاعدة بيانات وإذن إرسال آمن، تبقى محلية وقابلة للنسخ أو الحذف فقط.

### ميزات مؤجلة عمداً

لا تشمل المرحلة الأولى صوتاً، أو تدريباً لنموذج لغة، أو إرسالاً تلقائياً لتقارير المستخدمين، أو مزامنة سحابية، أو نموذجاً ضرورياً للتشغيل. هذه الحدود تجعلها مناسبة للهاتف والمشروع التعليمي وتمنع تحويل التفاعل إلى جمع بيانات غير مقصود.

## المرحلة الثانية — Specialized Local Merchant Model

تبدأ المرحلة الثانية فقط بعد قياس استخدام المرحلة الأولى ومراجعة اقتراحات المتاجر. هدفها ليس «تعليم التطبيق من محادثات المستخدمين»، بل إضافة طبقة نموذج **اختيارية ومحلية** لفهم الأوامر المركبة أو الصياغات الغامضة واقتراح structured commands ضمن العقد المغلق نفسه.

### ما الذي يمكن تطويره

يمكن مقارنة نموذج صغير مثل `Qwen/Qwen3-0.6B`، الذي تعرض صفحته الرسمية ترخيص Apache-2.0، بمسار Rules-only أو بنموذج مفتوح آخر. [1] لكن لا يفوز أي نموذج باسمه؛ يجب قياس حجم الوزن المرخّص، وقت التنزيل الأول، الذاكرة، الاستجابة العربية، سلوك WebGPU، وسلوك هاتف بلا WebGPU. توثق Transformers.js أن WebGPU ما زال تجريبياً في متصفحات كثيرة، لذلك لا يجوز جعله شرطاً للتطبيق. [2]

إذا احتاج المشروع لاحقاً نموذجاً أكثر تخصصاً، يُبنى ذلك من **مجموعة أمثلة اصطناعية أو متبرع بها صراحةً ومنزوعة الهوية** لأوامر التاجر والعقود المسموحة. لا تستعمل محادثات المتاجر الشخصية تلقائياً في التدريب. تدريب أو LoRA ليس مهمة هاتف أو متصفح في هذا المشروع؛ هو بحث مستقل لا يبدأ قبل وجود بيانات مرخصة، بيئة مجانية أو مفتوحة مثبتة، وخطة حذف وتراجع.

### بوابات المرحلة الثانية

| البوابة | شرط الانتقال |
|---|---|
| القيمة | تثبت المرحلة الأولى أن نسبة معتبرة من الأوامر الغامضة تعود بـ`needs-clarification` أو أن التجار يطلبون فهم صياغات غير مدعومة |
| الترخيص | ترخيص واضح يسمح بالاستخدام التعليمي والتوزيع المطلوب، وتوثيق مصدر الأوزان |
| الخصوصية | لا بيانات تاجر أو سجل محادثة ضمن تدريب النموذج من دون موافقة صريحة منفصلة |
| الأداء | قياسات واقعية أو `NOT VERIFIED`؛ لا تحميل تلقائي ولا كسر لمسار الإعلان المحلي |
| الأمان | كل مخرج structured يمر بـschema وallowlist وDesignContract وQuality Gate |
| التراجع | يمكن تعطيل النموذج وحذف cache الأوزان من دون فقدان Merchant Profile أو محرر الإعلان |

## معيار الإنجاز للمنافسة

ينفذ المتسابق **المرحلة الأولى كاملة فقط**: تبويبة المساعد، الإعداد المؤكد، ذاكرة محلية محدودة، أوامر typed، اقتراحات قابلة للتطبيق والتراجع، ومسودة تحسين محلية للمطور. المرحلة الثانية تقدم كـ`MODEL_SELECTION.md` و`ARCHITECTURE.md` وخطة benchmark؛ لا يقبل إدخال وزن نموذج في Git أو تحميله داخل الاختبارات الأساسية.
