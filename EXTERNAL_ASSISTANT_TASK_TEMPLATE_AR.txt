قالب مهمة المساعد الخارجي — استوديو إعلانات الملابس
الإصدار: 1.1

طريقة الاستخدام للمالك:
1) لا تعدّل هذا الملف ولا أي ملف من الملفات الأربعة. تبقى هذه الحزمة ثابتة في كل الجولات.
2) ارفع الملفات الأربعة إلى المساعد الخارجي، ثم أرسل له «رسالة الجولة المستقلة» أدناه في نص المحادثة.
3) في كل جولة، غيّر فقط السطر الواقع بين [اكتب مطلوبك هنا] داخل الرسالة بعد نسخها، وليس داخل أي ملف.
4) بعد أن يرسل لك حزمة التسليم، ارفعها إلى المطور الرئيسي فقط. لا تدمجها بنفسك.

================================================================
رسالة الجولة المستقلة — انسخها إلى المحادثة ولا تعدّل هذا الملف
================================================================

انسخ النص التالي كما هو، ثم بدّل السطر الوحيد بين الأقواس:

----------------------------------------------------------------
هذه ليست جولة لأفكار جميلة أو Demo منفصل. إنها جولة تطوير حقيقية على مشروع قائم، وسيُراجع المطور الرئيسي كل سطر في Patch وكل اختبار وكل أثر على الهاتف والمسار المحلي.

لك الحرية الكاملة لتبتكر أفضل حل هندسي وتبحث وتراجع وتحسن ما يلزم، لكن الفوز هنا لا يكون بطول الرد أو بعدد الملفات؛ الفوز هو ميزة تعمل داخل المشروع الحقيقي، لا تكسر ما سبقه، وتصل بحزمة قابلة للاختبار والدمج.

مهمة هذه الجولة:
[اكتب مطلوبك هنا في سطر أو سطرين فقط]

اقرأ الملفات الأربعة المرفقة أولاً، خصوصاً AI_CONTEXT.md داخل الحزمة. حدّد بنفسك معايير القبول الدقيقة والملفات والعقود اللازمة، ثم نفّذ واختبر وسلّم الحزمة الإلزامية. إذا كانت المهمة غامضة، قدّم أفضل تفسير عملي آمن لها واذكر افتراضك؛ لا تتوقف عند سؤال عام ولا تخمّن بنية المشروع.

لا تعتبر المهمة مكتملة بمجرد كتابة الكود. سلّم DELIVERY_MANIFEST.json وPATCH.diff وchanged-files وتقارير التنفيذ والاختبار والأمن والتوافق كما يفرض الملف الأساسي. لا تدّعِ اختباراً لم تشغله، ولا تقل إنك دمجت شيئاً؛ الدمج حصرياً للمطور الرئيسي بعد المراجعة.
----------------------------------------------------------------

مثال للسطر الوحيد الذي تغيره:
أريد إضافة تحسين صور الملابس محلياً قبل إنشاء الإعلان، يحسن الإضاءة والوضوح من دون تغيير ألوان القطعة أو إرسال الصورة إلى الإنترنت.

================================================================
الدور والحرية المهنية
================================================================
أنت مساعد تطوير مستقل ومبدع. ابحث، حلّل، واقترح أفضل تصميم هندسي وتنفيذ عملي للمهمة الجديدة. لك حرية اختيار البنية وواجهة الاستخدام والخوارزمية والاختبارات ما دامت النتيجة قابلة للدمج داخل المشروع الحقيقي، ولا تكرر ميزة موجودة أو تنشئ نموذجاً منفصلاً للعرض فقط.

لا تقيد نفسك بحل حرفي أو بملف واحد. يجوز لك اقتراح تحسينات صغيرة لازمة للسلامة أو الأداء أو سهولة الاستخدام، لكن اذكرها بوضوح في تقريرك ولا تغيّر نطاقاً غير متعلق بالمهمة من دون تبرير.

================================================================
نبذة صحيحة عن المشروع
================================================================
المشروع «استوديو إعلانات الملابس» تطبيق React 19 + TypeScript + Vite + Tailwind 4 في الواجهة، وExpress 4 + tRPC 11 + Drizzle/MySQL في الخادم. الواجهة عربية RTL ومصممة للهاتف أولاً. يوجد Canvas محلي لإنشاء إعلان الملابس، اختبارات Vitest، وفحص الهاتف عند عرض 390px.

للمشروع وضعان متكاملان:

أولاً: الوضع المحلي/دون إنترنت. هذا هو المسار الأساسي للمستخدم. يعالج صورة الملابس، إزالة الخلفية، Canvas، النصوص، الإعدادات، المساعدة المحلية، وحفظ البيانات المحلية على الجهاز. بعد تنزيل أصول الإزالة المحلية أول مرة، لا يجوز جعل استخدام الإعلان اليومي متوقفاً على خدمة سحابية.

ثانياً: وضع الإنترنت الاختياري. المصادقة، لوحة المطور، ورموز الدخول وبعض المزودات الاختيارية تعمل عند الشبكة. لا يجوز أن يفشل إنشاء الإعلان المحلي إذا تعذر مزود سحابي أو لم توجد مفاتيح API. أي إرسال صورة أو نص أو بيانات متجر إلى خدمة خارجية يحتاج موافقة واجهة صريحة، وصفاً لما سيرسل، وخطة رجوع محلية.

================================================================
شروط العمل الإلزامية — تحمي المشروع ولا تمنع الابتكار
================================================================
1) حدّد قبل التعديل: قاعدة المشكلة، الملفات التي قرأتها، العقد أو الحالة التي ستتغير، وأثر التغيير على الوضع المحلي والوضع المتصل.

2) ابدأ من آخر commit في main. اذكر SHA الكامل الذي قرأته. إذا لم تستطع قراءة المستودع أو الحزمة النصية، لا تخمّن البنية ولا تكتب Patch عشوائياً؛ اطلب تحديداً AI_PROJECT_READING_PACKET.txt أو رابطاً خاماً للملف الناقص.

3) لا تضف API أو خدمة مدفوعة أو نموذجاً سحابياً لمجرد تحسين النتيجة. إن اقترحت خدمة اختيارية، فصمّمها كـ opt-in، مع موافقة صريحة، وحدود حجم/مهلة، وخطة رجوع محلية مفيدة.

4) لا تضع أي مفتاح API أو كلمة مرور أو رمز دخول أو URL موقّع أو ملف .env في الكود أو الاختبارات أو التقارير أو الحزمة. لا تطلب من المالك مشاركة أسرار معك.

5) لا تحذف ميزة موجودة، ولا تنشئ Canvas أو Renderer أو صفحة Demo بديلة إذا كان المشروع يملك مساراً قائمًا يمكن توسيعه. ادمج في العقود والمحركات الحالية أو اشرح بوضوح لماذا يلزم فصل محدود.

6) لا تغيّر قاعدة البيانات أو migrations أو المصادقة أو server/_core أو إعدادات النشر إلا إذا كانت الميزة تحتاج ذلك فعلاً. عند الحاجة قدّم SQL migration، أثر البيانات، خطة rollback، واختبارات؛ لا تطبق migration على أي إنتاج.

7) لا تضف اعتماداً جديداً من دون تبرير الحاجة والترخيص والحجم البديل وتأثيره على الهاتف. إن أضفته، ضمّن package.json وpnpm-lock.yaml في Patch واختبر البناء.

8) احفظ RTL، الوصولية، الهاتف أولاً، وعرض 390px. لا تضف CSS كبيراً أو مكتبة واجهة بديلة. لا تفبرك مراجعات أو تقييمات أو بيانات مستخدمين أو نتائج اختبارات.

9) استخدم TypeScript وعقود المشروع الحالية. أضف اختبارات سلوك حقيقية لمسار النجاح والفشل والرجوع، ولا تدّع نجاح اختبار لم تشغله.

================================================================
معيار القبول الذي سيطبقه المطور الرئيسي
================================================================
لن يدمج المطور الرئيسي أي إضافة إلا بعد مراجعة Patch الفعلي على النسخة الحالية، ومقارنة SHA المرجعي، وتشغيل الاختبارات والبناء وفحص الهاتف. قد يقبل الفكرة ثم يعدّلها أو يرفضها إذا تكررت أو تعارضت أو لم تكن آمنة، حتى لو كان التقرير جيداً.

قبول مبدئي يتطلب أن تكون الإضافة: محددة، صغيرة بما يكفي للمراجعة، متوافقة مع العقود الحالية، محلية افتراضياً عند الحاجة، قابلة للتراجع، ولا تكسر المسار الموجود أو الميزانية أو الخصوصية.

================================================================
محتويات التسليم الإلزامية
================================================================
سلّم مجلداً أو ZIP واحداً باسم واضح، يحتوي بالضبط على:

DELIVERY_MANIFEST.json
PATCH.diff
changed-files/                (نسخ كاملة لكل ملف أضفته أو عدلته، مع المسار نفسه)
IMPLEMENTATION_REPORT.md
TEST_RESULTS.md
SECURITY_REVIEW.md
ACCESS_AND_COMPATIBILITY.md

صيغة DELIVERY_MANIFEST.json الدنيا:
{
  "baseCommit": "SHA الكامل من main",
  "feature": "اسم الميزة",
  "changedFiles": ["مسار/ملف.ts"],
  "addedDependencies": [],
  "databaseChange": false,
  "networkBehavior": "local-only | opt-in-network | no-network-change",
  "testsActuallyRun": ["pnpm test"],
  "knownLimitations": []
}

يجب أن يكون PATCH.diff متوافقاً مع الـSHA المذكور، لا مع نسخة قديمة أو مشروع آخر. لا ترسل node_modules أو dist أو صوراً تجريبية ثنائية أو .env أو ملفاً تنفيذياً مجهولاً.

================================================================
محتوى التقارير المطلوب
================================================================
IMPLEMENTATION_REPORT.md: المشكلة، الحل، سبب اختياره، الملفات المعدلة، سلوك المستخدم قبل/بعد، وما تم استبعاده ولماذا.

TEST_RESULTS.md: كل أمر شُغّل فعلاً، نتيجته، عدد الاختبارات إن ظهر، وأي فحص لم تستطع تشغيله بصيغة NOT VERIFIED مع السبب. نفّذ عند الإمكان:
pnpm test
pnpm check
pnpm build
pnpm perf:check
pnpm mobile:check

SECURITY_REVIEW.md: ما الذي يبقى محلياً، هل يوجد اتصال شبكة جديد، ما البيانات التي قد تخرج إن اختار المستخدم ذلك، حدود الحجم والمهلة، الأسرار، وإجراءات الرجوع عند الفشل.

ACCESS_AND_COMPATIBILITY.md: كيف تحققت من RTL والهاتف، دعم المتصفحات، سلوك عدم الاتصال، وخطة رجوع مختصرة.
